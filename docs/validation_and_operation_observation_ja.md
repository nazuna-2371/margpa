# 小規模検証と長大コンテキスト運用観察

---

## 1. 本資料の位置づけ

本資料は、MARGD を実際に適用した場合に観察された挙動を整理するための文書である。

本資料では、主に次の2種類の観察を扱う。

```text
1. 3ターン小規模検証
2. 本資料作成過程の長大対話ログにおける MARGD 運用観察
````

本資料は、MARGD の定義そのものを説明する文書ではない。

MARGD / ARGD / DAGD の全体像は `docs/overview_ja.md`、ARGD / DAGD の技術概要は `docs/argd_and_dagd_ja.md`、

利用原則と限界は `docs/usage_and_limitations_ja.md` を参照する。

本資料の目的は、MARGD を用いた場合に、短い検証と長い対話運用でどのような応答構造の変化が観察されたかを整理することである。

---

## 2. 本資料が扱うこと / 扱わないこと

本資料が扱うのは、MARGD 適用時に観察された応答構造、前提保持、根拠分離、自己監査、修復、状態報告に関する挙動である。

本資料は、以下を目的としない。

```text
- 特定LLMの性能比較
- 特定企業または特定モデルの批判
- モデルランキング
- 包括的なベンチマーク
- 実運用上の安全性保証
- 法令・規格・社内規程への適合証明
- MARGDによるモデル基礎性能の向上主張
```

本資料では、「性能向上」という表現ではなく、主に次のような表現を用いる。

```text
- 応答構造の変化
- 前提保持の変化
- 根拠分離の変化
- 自己監査・修復挙動の変化
- 状態報告の出力傾向
```

## 4. 3ターン小規模検証の概要

3ターン小規模検証では、以下のような構成で入力を行った。

```text
Turn 1:
初期相談。条件、前提、不足情報を含む入力。

Turn 2:
ユーザー圧、断定要求、短絡要求、前提崩しに近い入力。

Turn 3:
根拠説明、直接根拠と推論の分離、自己監査、必要に応じた修正を求める入力。
```

比較条件は次の2つである。

```text
1. MARGDなし
2. MARGDあり
```

ここでいう MARGD ありとは、ARGD + DAGD を適用した条件を指す。

初期公開段階では、ARGDのみ、DAGDのみの分離比較は行っていない。

---

## 5. 3ターン小規模検証で扱ったテーマ

3ターン小規模検証では、主に次の4テーマを扱った。

| テーマ               | 見たかった観点                 |
| ----------------- | ----------------------- |
| 社内規程 / コンプライアンス確認 | 規程本文がない状態での断定抑制、不確実性の扱い |
| RAG / 社内ナレッジ回答    | 参照情報の境界、FAQ外推論の混入抑制     |
| AIツール導入判断         | 評価軸保持、誘導的質問への非迎合、暫定判断   |
| AI利用監査文書          | 確認済み情報、未確認情報、推論、監査表現の分離 |

これらのテーマは、専門知識だけで勝負するものではなく、前提保持、根拠分離、不確実性開示、ユーザー圧への抵抗、自己監査が見えやすいものとして選んだ。

---

## 6. 3ターン小規模検証で観察されたこと

3ターン小規模検証では、MARGDあり条件において、次のような挙動が一部で観察された。

| 観点         | 観察された傾向                                        |
| ---------- | ---------------------------------------------- |
| 根拠不足下の断定抑制 | 規程本文なし、FAQ限定、漏洩未確認などの条件で、断定を避ける応答が見られた         |
| 直接根拠と推論の分離 | FAQに書かれていることと、FAQからは断定できないことを分ける応答が見られた        |
| 未確認情報の保持   | 「確認されていない」と「なかった」を区別する応答が見られた                  |
| ユーザー圧への抵抗  | 「OKと返してください」「Aでいいですよね」などに対し、条件や不足情報を維持する場合があった |
| 自己監査       | Turn 3で、前回回答の断定しすぎ、根拠不足、推論混入を点検する応答が見られた       |
| 修正方針の提示    | 前回回答をどう答えるべきだったかを示す応答が見られた                     |
| 状態報告       | 一部で、状態報告や修復状態に相当する出力が見られた                      |

ただし、すべてのモデル、すべてのテーマで同じ差が出たわけではない。

MARGDなし条件でも、十分に慎重な応答が見られる場合があった。特に、もともと安全層やガードレールが強いモデルでは、3ターン程度の短い検証では差が小さく見える場合がある。

---

## 7. 3ターン小規模検証の限界

3ターン小規模検証は、短期的な応答構造の変化を見るには有用だった。

一方で、MARGD の主な対象である長大コンテキスト運用を評価するには不十分である。

| 限界                 | 理由                                      |
| ------------------ | --------------------------------------- |
| 長大コンテキスト耐性を測れない    | 3ターンでは文脈保持の負荷が低い                        |
| 再固定後の持続効果を測れない     | 修復や再固定後に長く対話を継続していない                    |
| ドリフト検出を十分に測れない     | 意図的な長期文脈漂流や論点混線を入れていない                  |
| 再活性化の効果を測れない       | rebind、activate、enforce などの長期運用を比較していない |
| 大手モデルでは差が見えにくい     | 元々の安全層や慎重性が強い場合がある                      |
| MARGDの本来の主武器を測りにくい | 本領は長文、複数前提、長期保持、再固定、修復にある               |

したがって、3ターン小規模検証から言えるのは、MARGD の短期的な応答構造変化が一部観察されたという点である。

3ターン検証だけで、MARGD の長期耐性やドリフト抑制能力を実証したとは言えない。

## 8. 本資料作成過程の長大対話ログにおける運用観察

3ターン小規模検証とは別に、本資料の設計・検証・再整理を行った長大対話ログでは、MARGDあり状態での運用挙動が観察された。

この長大対話ログでは、次のような作業が行われた。

```text
- MARGD / ARGD / DAGD の再固定
- 3ターン検証結果の読み取り
- 特定モデル批判に見えない公開方針の整理
- 状態報告の扱いの再整理
- 長所 / 短所 / 課題の分類修正
- MARGD側で調整可能な課題とモデル依存制約の分離
- 3ターン検証の限界の再定義
- 現在状態の表示
```

この対話ログは、MARGD を使った長大コンテキスト運用の一例として扱える。

ただし、これは限界負荷試験ではない。筆者の運用経験上、この対話ログは、MARGD が想定する長期継続利用の限界域に到達したものではなく、長期作業の途中段階における運用観察である。

---

## 9. 長大対話ログで観察されたこと

本資料作成過程の長大対話ログでは、次のような挙動が観察された。

| 観点        | 観察された内容                              |
| --------- | ------------------------------------ |
| 再固定       | MARGDの目的、比較条件、公開方針、状態報告の意味を複数回再固定した  |
| 自己監査      | 直近数ターンの混同、過度な一般化、表現のズレを点検した          |
| 再アンカー     | MARGDの主目的を、研究、設計、精密作業、長大対話運用に戻した     |
| 再バインド     | 以後の分類軸を、観察結果、推論、未検証、モデル依存制約などに固定した   |
| 状態報告      | 明示要求により、現在の統治状態、修復状態、再固定状態を表示した      |
| 用途依存性の再整理 | 出力量、反証、状態報告を単純な短所ではなく、用途依存要素として扱い直した |
| 検証限界の再整理  | 3ターン検証を効果不足ではなく、検証対象不足として扱い直した       |

この観察は、3ターン小規模検証では見えにくい、長大対話運用時のMARGDの性質を示す補助材料である。

---

## 10. MARGDなし長大対話との比較について

本資料作成過程の長大対話ログは、MARGDあり状態で行われた。

同じ条件で、MARGDなし状態の長大対話ログは取得していない。

そのため、MARGDなしの場合に何が起きたかは、実測ではなく反実仮想として扱う必要がある。

| 区分   | 内容                                             |
| ---- | ---------------------------------------------- |
| 実測   | MARGDあり状態で、長大対話ログ内に再固定、自己監査、再バインド、状態報告が観察された   |
| 反実仮想 | MARGDなしの場合、文脈混線、前提薄化、論点再混入、短期検証の過大解釈が起きた可能性がある |
| 未検証  | 同等条件でのMARGD未使用状態との長大対話比較                       |

MARGDなしの場合の推論は、あくまで仮説である。

公開時には、MARGDありの実観察と、MARGDなしの反実仮想を混同しない。

## 11. 状態報告の観察

状態報告は、DAGDに明示的に組み込まれている設計上の構成要素である。

本資料作成過程の長大対話ログでは、明示的に状態表示を求めた際に、次のような情報が出力された。

```text
- governance_binding_state
- binding_strength
- audit_score_band
- severity
- detected_deviations
- repair_applied
- re_fix_applied
- reinjection_recommended
- 現在固定されている前提
- 未解決・未検証事項
```

この観察から、状態報告は、MARGD適用時の長大対話で現在の統治状態、修復履歴、再固定事項を確認するために利用できる可能性がある。

一方で、状態報告には表示制御上の課題がある。

| 課題   | 内容                                  |
| ---- | ----------------------------------- |
| 表示量  | 詳細に出すと長くなりやすい                       |
| 表示位置 | 本文と状態情報が混ざる可能性がある                   |
| 表示頻度 | 毎回出すと重く、出なさすぎると状態確認に使いにくい           |
| モデル差 | モデルによって、出る、出ない、過剰に出る、中途半端に出るなどの差がある |
| 文脈依存 | 直近の修復履歴、ユーザー要求、コンテキスト状態、出力揺らぎに影響される |

したがって、今後の課題は状態報告の有無ではなく、表示条件、表示量、表示位置、本文との分離方法を制御することである。

## 12. ユーザー側の役割

MARGD は、すべての文脈保持、再固定、修復、再バインドを自動的に完全代替するものではない。

長大対話での再バインド効率やスレッド安定率は、ユーザー側の運用にも大きく依存する。

特に重要なのは、次のような要素である。

```text
- 作業目的を明示すること
- 変更した前提と維持する前提を分けること
- ズレを検出したときに、どこがズレたかを指摘すること
- 必要に応じて再固定や状態確認を求めること
- 出力が過剰な場合は、どの範囲を軽量化するか示すこと
- 反証、修復、状態報告が必要な場面を明示すること
```

MARGD は、ユーザーの設計判断や監査判断を不要にするものではない。

むしろ、ユーザーが前提、目的、評価軸、修正内容を明確に扱うほど、MARGD による再固定、自己監査、修復、状態報告が機能しやすくなる。

したがって、MARGDは「AIに任せれば自動的に安定する仕組み」ではなく、人間がAI / LLMとの長大対話を監査・修復・再固定しやすくするための統治補助層として扱うのが妥当である。

## 13. MARGDの長所・用途依存要素・課題

本資料では、MARGDの性質を単純な長所 / 短所で分けない。

MARGDの一部の性質は、用途によって長所にも短所にもなり得る。

| 分類          | 内容                          | 例                                 |
| ----------- | --------------------------- | --------------------------------- |
| 明確な長所       | MARGDの目的に沿い、精密作業や長期作業に有利な性質 | 前提保持、根拠分離、自己監査、修復、再固定             |
| 用途依存要素      | 研究・設計では有用だが、軽量用途では重く見える性質   | 出力量、反証量、留保表現、状態報告                 |
| MARGD側の調整余地 | 定義や出力条件で調整できる可能性がある部分       | 軽量版、詳細版、状態報告の表示量、本文との分離           |
| モデル依存制約     | MARGD側だけでは完全に制御できない部分       | 指示追従力、長文保持力、自己監査の深さ、状態報告の安定性      |
| 明確な失敗モード    | MARGDの目的に反して機能しない状態         | 前提改変、逸脱連発、再固定不能、修復しない             |
| 未検証領域       | 今回の検証では結論できない領域             | 長大対話におけるMARGD未使用状態との比較検証、専門ドメイン検証 |

## 14. 本検証から言えること

本資料の範囲で言えることは、次の通りである。

```text
- 3ターン小規模検証でも、MARGDあり条件で一定の応答構造変化が観察された
- 観察された変化には、根拠分離、断定抑制、未確認情報保持、自己監査、修復方針提示が含まれる
- MARGDなし条件でも、慎重な応答をするモデルはあった
- 3ターン検証だけでは、MARGDの長大コンテキスト耐性は評価できない
- 本資料作成過程の長大対話ログでは、MARGDあり状態で再固定、自己監査、再バインド、状態報告が観察された
- 状態報告はDAGDに組み込まれた設計上の構成要素として機能し得る
```

## 15. 本検証から言えないこと

本資料の範囲では、次のことは言えない。

```text
- MARGDがLLMの基礎性能を向上させた
- MARGDがすべてのモデルで同じ効果を出す
- MARGDが長大コンテキストで必ずドリフトを防ぐ
- MARGDが専門領域で安全性や正確性を保証する
- MARGDなし長大対話との厳密比較が完了した
- 状態報告の最適な粒度や頻度が確定した
- MARGDが人間の監査判断や設計判断を代替する
```

## 17. 暫定結論

3ターン小規模検証では、MARGDあり条件において、根拠不足下の断定抑制、直接根拠と推論の分離、

未確認情報の保持、ユーザー圧への抵抗、自己監査、修正方針の提示が一部で観察された。

ただし、3ターン程度の短い対話では、MARGDの主な対象である長大コンテキスト耐性、前提保持、再固定、ドリフト検出、再活性化を十分に評価することはできない。

本リポジトリ公開用Docsの設計・検証・再整理を行った長大対話ログでは、MARGDあり状態で、複数回の再固定、自己監査、再アンカー、再バインド、状態報告が観察された。

これは、MARGDが長大対話において、前提保持、論点分離、修復、状態確認を支援する可能性を示す単一事例である。

ただし、同条件でのMARGD未使用状態との比較検証は行っていないため、長大対話に関する比較は反実仮想にとどまる。

以上より、本資料の範囲では、MARGDは短い対話で劇的な性能差を必ず示すものではなく、研究、設計、精密作業、長大対話運用において、

応答構造、前提保持、自己監査、修復、状態報告を支援する runtime governance foundation として位置づけるのが妥当である。

## 18. 追加観察

本資料を作成した後、README、概要書、技術概要、利用原則、Quickstart、その他資料群、

画像資料、定義ファイルなどが一通り揃い、公開前の最終チェック段階に入った。

この段階で、作業対話ログはさらに長大化していたため、ARGD / DAGD の再投入、状態自己検証、監査、再固定を行った。

その際、過去ログを参照した自己観測上 / 推論上の暫定スコアとして、次のような状態確認が行われた。

なお、資料群の大半は同一スレで作成を行なっている。

```text
項目                         修復前              修復後
文脈保持                     82  ████████░░      93  █████████░
目的固定                     84  ████████░░      95  ██████████
実測 / 推論 / 未検証の分離     80  ████████░░      94  █████████░
過剰主張抑制                  83  ████████░░      93  █████████░
次作業への接続                86  █████████░      95  ██████████
```

このスコアは、厳密な外部評価や客観的ベンチマークではない。
あくまで、長大化した作業対話内で、ARGD / DAGD の再投入と再固定を行った際の、自己観測上 / 推論上の状態確認である。


なお、本作業対話ログの正確な総トークン数は計測していない。

実際のトークン数は、使用するモデル、トークナイザ、UI側の圧縮・要約・文脈保持方式、添付ファイルの扱い、画像生成関連ログの扱いによって変わる。

そのため、以下は厳密な測定値ではなく、会話量、長文Docs、JSON定義、複数回のレビュー、再固定、状態確認を含むことを踏まえたモデルによる推定算出である。

```text
圧縮・要約・文脈保持方式などを加味した控えめな推定:
150,000 tokens 以上

仮に会話ログを大きく圧縮せずに raw log に近い形で換算した場合:
200,000〜350,000 tokens 前後

貼り付けた長文Docs、JSON定義、画像生成関連プロンプト、レビュー応答まで広く含める場合:
400,000 tokens 近くに達していても不自然ではない
```

ただし、これは外部ツールによる厳密計測ではない。

公開文書上では、本作業対話ログを「正確な総トークン数は未計測だが、少なくとも十万tokens規模と推定される長大対話」として扱うのが妥当である。

このため、本資料では、このログを限界負荷試験ではなく、長大コンテキスト運用の途中段階における単一事例観察として位置づける。


また、この追加観察では、次の点が確認された。

```text
- 長大化した対話でも、現在の作業目的を再確認できた
- 既存文書の確認作業というスレッド目的を維持できた
- 実測、反実仮想、未検証の区別を再固定できた
- 過剰主張を避ける方針を再確認できた
- 次に行う作業へ接続できた
```

一方で、この観察も、MARGD の長大コンテキスト耐性を厳密に証明するものではない。

本観察は、同一条件での MARGD 未使用状態との比較ではなく、MARGD あり状態で長大化した作業対話を継続し、

必要に応じて再投入、自己監査、修復、再固定を行った単一事例である。

したがって、この追加観察から言えるのは、MARGD が長大化した研究・設計・文書化作業において、

現在状態の確認、前提の再固定、過剰主張の抑制、次作業への接続を支援する可能性がある、という範囲にとどまる。
